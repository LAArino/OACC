# OECP: owner decisions log

Answers to the questions of `docs/review/00-consolidated-pending-decisions.md`. Date: 2026-10-14.

| # | Decision | Answer |
|---|---|---|
| 1 | MVP scope for identity | No wallet. Authentication with Keycloak (local) and eduGAIN federation. |
| 2 | Ownership and GDPR | The code is released by the author (Lluís Alfons Ariño), with no co-authors, under EUPL v1.2. First application: the Aurora alliance. The Aurora Foundation is the **controller** (it decides what is published and manages the administrators). URV hosts the MVP infrastructure and acts as **processor**; a processing agreement (GDPR art. 28) between the two is required. |
| 3 | Channel A: pull or push | **Pull only** in the MVP: a scheduled harvester against each partner's OEAPI (daily by default, a "sync now" button in the panel). Withdrawals by absence in a complete harvest. The notification route ("harvest now") and any push of data are out of the MVP. |
| 4 | Partner inventory | With OEAPI in the latest version: UIBK, UICE, VUA, UDE. Without OEAPI: URV, UNINA, UP, CBS, UPEC and the Aurora Foundation itself. Several have stated that they have no technical capacity, hence the form and the CSV upload. |
| 5 | Multilingualism | MVP in English, mandatory. By design, the portal must be able to be consulted in the language of each partner university, with English as the fallback when a piece of content has not been supplied in that language. |
| 6 | Natural key and lifecycle | (default, proposed 2026-10-14) Unique key per organization + course code; states draft / published / withdrawn / cancelled; the partner unpublishes by changing the state from any channel. |
| 7 | Delivery-mode vocabulary | (default) That of OEAPI v6 (online, presential, hybrid, blended, coil…), with no distinction between synchronous and asynchronous. |
| 8 | Remaining seats | (default) Shown only if the partner reports them, with the date of the latest figure; otherwise, only the seats reserved for the alliance. |
| 9 | Roles and account creation | (default) Roles `partner_admin` and `alliance_admin` with an organization claim; the global admin invites the partner admins; MFA mandatory for administrators. |
| 10 | Stack and team | Development by the owner with Claude's assistance. NestJS + Vue 3/Nuxt + Traefik + PostgreSQL. Deployment deliverables: Docker Compose (MVP) and a Helm chart, so that other alliances can adopt the solution quickly. |
| 11 | Language and governance | (default) Monorepo, English in code and documentation, DCO with inbound = outbound EUPL v1.2. |
| 12 | Mixed channels | (default) One authoritative channel per organization; manual edits to harvested data are stored as explicit overrides that survive the next harvest. |
| 13 | The partners' OEAPI endpoints | The OEAPI endpoints of UIBK, UICE, VUA and UDE are the same ones that eduXchange harvests (confirmed by the owner). |
| 14 | Access route to the OEAPI endpoints | **Directly to each university** (UIBK, UICE, VUA, UDE), with a credential and a bilateral agreement per partner, to minimise dependencies on SURF. The SURFeduhub mode remains only as a fallback alternative. |
| 15 | Registration of the SP in the federation | Confirmed: a single SP registered in SIR (RedIRIS) with export to eduGAIN and multi-ACS metadata; VUA via SURFconext, CBS via WAYF. |
| 16 | Erasmus+ and EUPL | Confirmed by the owner: the terms of the grant agreement allow publication under EUPL v1.2. |
| 17 | Onboarding guides (after the first version is closed) | Create four guides in `docs/onboarding/`: (a) alliance (deployment, the Foundation as controller, registration of organizations and of the first admin); (b) university with an OEAPI in operation for eduXchange (grant direct access to OECP: URL, credential, allowlist, profile `consumer=eduxchange`); (c) university without eduXchange but with integration capacity (implement an OEAPI v5 endpoint or automate the generation of the CSV); (d) university without integration capacity (web form and CSV upload). Pending until the version is validated and closed. Technical complement (added 2026-10-14): data-provider guides in `docs/guides/`: integration via API, CSV generation and use of the web form. |
| 18 | Alliance attributes and parity with the Aurora Virtual Campus (confirmed 2026-10-14) | (a) `course_attributes` JSONB per course, validated against a schema that each alliance defines in its deployment (Aurora: educational hub, SDGs, competence framework, micro-credential, free course, enrolled students only, open to the whole alliance, target audience); the portal shows them as configurable labels and filters. (b) `course_kind` (course / bip / lecture_series / other). (c) Multilingual text `application_instructions` on the offering, next to `application_url`; functional contacts, not personal ones. (d) Multi-valued level on the course. (e) Sorting by application deadline in the catalogue. All in the MVP. The concrete list of Aurora attributes is agreed with the Foundation before migrating the 13 current course records. Planned after the CSV console. |
| 19 | `consumer` on the read API `/oeapi/v5` (confirmed 2026-10-14) | Strict semantics of the standard: with no parameter or with `consumer=oecp` the published catalogue is returned; any other value (for example `eduxchange`) returns an empty page. eduXchange keeps harvesting each partner directly. Reversible in one condition of `OeapiService` if the alliance decides to offer the aggregated catalogue to eduXchange, subject to prior agreement with the partners and SURF. |
| 20 | Offerings without a usable teaching language (confirmed 2026-10-14) | The rejection is kept: an offering whose language (its own or inherited from the course) is `mul`, `und`, `zxx`, `mis` or missing is rejected with `oecp.oeapi.missing_teaching_language` and remains visible in the partner's synchronisation monitor. The catalogue never publishes offerings without a concrete language. |
| 21 | Alignment with the data model of the IT Handbook §3.4 (confirmed 2026-10-14) | (a) **Instructors**: field `instructors` (list of names) per course, optional for each partner to fill in; legal basis documented (public interest; data that the universities already publish in their catalogues); harvested from OEAPI `coordinators` when these come expanded with a name. (b) **Five optional texts**, multilingual: mode of repetition, methods, literature, privacy notice, remarks. (c) **Publication rule** of the Handbook (all mandatory fields present for a course to be shown): implemented with a transition period in "warning" mode (`OECP_PUBLISH_RULE=warn`, the panel and the synchronisation report point out what is missing, without blocking) and an `enforce` mode that can be enabled per deployment. (d) **Attributes not agreed**: those of the current website are kept (micro-credential, free, enrolled students only, open to the alliance, target audience, course type) as Aurora attributes. |
| 22 | Sign-in mode per organization: local or federated, never mixed (confirmed 2026-10-15) | (a) **The alias decides**: the `keycloak_idp_alias` field of each organization sets the mode of all its administrators. (b) **Local** (alias NULL): Keycloak local accounts with a password of at least 12 characters and TOTP, set up from the e-mail that Keycloak sends on invitation; no self-registration and no open password reset (recovery with *Resend set-up e-mail* in the organization's *Administrators* panel). This is the mode of the alliance organization (Aurora Foundation) and of the universities that are not in eduGAIN or are not yet connected. (c) **Federated** (alias set): SAML sign-in with the university's IdP via eduGAIN, plus a TOTP that OECP registers after the first sign-in. (d) **Migration local → federated**: enable the IdP in the realm, set the alias and invite the administrators again; the wrong mode is rejected (`oecp.invitation.mismatch`, and `oecp.auth.idp_mismatch` for the accounts of the previous mode). (e) **No mixed mode**: an organization with some local and some federated administrators is neither allowed nor planned. Reversible later, by making the mode a property of each invitation, if a real case arises. |
| 23 | Retention of e-mail addresses in the audit log (confirmed 2026-10-15) | Kept as implemented: `audit_log.changes` keeps the address of the invited or revoked administrator in clear for 36 months (`OECP_RETENTION_AUDIT_MONTHS`), as evidence of who received or lost access; no hashing or truncation. Reflected in the RoPA (activity 3). |
| 24 | Role of the partner universities with respect to the republished data (confirmed 2026-10-15) | **Independent controllers**: each university is the controller of the data it supplies (instructors, contacts) and the Aurora Foundation of the published catalogue; there is no joint controllership under art. 26. Each partner's bilateral access agreement (art. 28 checklist, section B) records this. |
| 25 | Brand images of the portal (confirmed 2026-10-15) | (a) **Header image** of the home page: a photograph generated by us (no third-party rights and no real people); the photo from the Aurora website is not used. (b) **Image of the course list**: an illustration generated by us. (c) **Aurora logo** in the site header: the Foundation has given permission to use it. The images are deployment configuration (`deploy/compose/branding/`), never repository content. Per-course images (proposal analysed on 2026-10-15) remain undecided. |
| 26 | Dormancy, account clean-up and recertification during the pilot (confirmed 2026-10-15) | (a) The `dormancy` (180 days) and `account-cleanup` (12 months) jobs stay in **dry run** (`OECP_DORMANCY_DRY_RUN=true`, `OECP_ACCOUNT_CLEANUP_DRY_RUN=true`) during the pilot; the alliance reviews the dry runs every quarter and the Foundation decides to activate them before opening the portal to the Internet (go-live checklist of Guide A). (b) Periods unchanged. (c) **Manual annual recertification**: review of the *Administrators* panels with the Foundation once a year; the automatic campaign (e-mail with confirm/revoke per administrator) stays in the backlog until the number of real administrators justifies it. Documented in `docs/onboarding/administrator-lifecycle.md`. |
| 27 | Images per course (confirmed 2026-10-16) | Decision 23 of the analysis of 2026-10-15, taken as recommended: (a) one image **per course**, inherited by its offerings; (b) a **copy stored in OECP** (uploaded in the web form or fetched by the worker from a URL in the CSV, re-encoded without metadata into fixed sizes, kept on the `uploads` volume and served from the portal's origin), never links to external servers; (c) provided by the **university** (CSV or form) or by the **alliance office** as an override on harvested courses; (d) **no identifiable people**; (e) **alternative text mandatory** in English (or explicitly decorative) and a credit or licence per image, declared by whoever uploads it; (f) the partner's logo as the fallback when a course has none. (g) The photographs of the current Aurora Virtual Campus website are **not migrated**; the header and course-list images of the portal are generated by the alliance itself (AI-generated, no third-party rights). To be built in a later release (backlog). |
| 28 | Partner university logos in the catalogue (confirmed 2026-10-16) | The Aurora Foundation has given permission to show the logos of the nine partner universities in the alliance catalogue (course cards and course pages), next to the university's name. They are deployment files, never repository content: `partner-<slug>.svg` (or `.png`/`.webp`) in the branding directory, supplied in their official form by the Foundation or by each university; the development stack uses text placeholders until the official files arrive. Decision 25 covers the alliance logo and the header images. |
| 29 | Federation through the SIR2 hub (IN PROGRESS, not confirmed; 2026-10-27) | Candidate decision, pending a test in the SIR2 test environment and the alliance's choice of production registration. Facts from URV IT and RedIRIS (2026-10-21, 2026-10-26 and 2026-10-27): (a) OACC is registered in SIR2, which publishes it to eduGAIN through a proxy; OACC configures **one** SAML identity provider (the SIR2 hub) and every university is chosen in the eduGAIN discovery service, which remembers the last choice (no hint parameter); (b) the hub can send a **`pairwise-id`** (derived from `uid` and `schacHomeOrganization`; it changes only if either changes); eduPersonTargetedID is deprecated and will not be used; (c) `schacHomeOrganization` is usually released but not guaranteed for every federation's hub: an organization whose users do not assert it uses local accounts (decision 22); (d) encrypted assertions, signed AuthnRequests and single logout are supported; the SP may request Personalized Access, CoCo v2 and R&S, and attribute release can be limited; (e) a test registration in test.sir2.rediris.es is possible, test accounts of foreign IdPs are not; RedIRIS agreed on 2026-10-27 to register OACC there releasing `pairwise-id`, `schacHomeOrganization`, `mail` and `displayName`, and moving to production means only pointing OACC at a different metadata URL; (f) eduGAIN makes **no attribute mandatory**, only recommended ones (eduGAIN attribute profile, GN3-11-012): the SP declares what it expects, each IdP decides what to release, and the set must be **agreed within the alliance**; proposed: `pairwise-id` and `schacHomeOrganization` required (sign-in refused with an explanatory message otherwise), `mail` also required (the API compares it with the invited address at acceptance) and `displayName` requested but optional; the hub builds `pairwise-id` from `uid` and `schacHomeOrganization` and stops with an error if either is missing, so each university must release both to the hub (2026-10-28; an `eduPersonPrincipalName` fallback has been asked to RedIRIS); the agreements by party are in the sign-in paths guide (`docs/onboarding/identity-paths.md`); (g) **scope is enforced by SIR2 only for its own IdPs**: other federations may pass the IdP's value through or rewrite it (UNIFICAT, for example, rewrites URV's to `urv.cat`), so OACC cannot rely on the federation to filter scoped attributes; mitigation: federated administration access always needs a personal invitation in addition to the `schacHomeOrganization` match, which is checked on every request; (h) the existing Aurora proxy `es.urv.aurora` publishes its IdP side at `https://fpp.sir2.rediris.es/es.urv.aurora/saml2/idp/metadata.php` (entity ID `https://fpp.sir2.rediris.es/es.urv.aurora/idp`, HTTP-Redirect SSO and SLO, transient NameID only, so the identifier travels as an attribute); the metadata are **unsigned** and carry no `validUntil`, and the RedIRIS certificate is valid until 2036-03-24, so the certificate is **pinned** in the realm instead of the signature-checked refresh of ADR 0017; a certificate change on either side is notified by hand to the contacts given in the registration form. Design consequences under evaluation (ADR 0018 to amend ADR 0004): one IdP alias shared by all federated organizations (drop the alias uniqueness), principal attribute `pairwise-id`, `schacHomeOrganization` mandatory for federated organizations (organization value or its partner's) and checked at invitation acceptance **and on every request**. Open: the test.sir2 IdP metadata URL and which accounts can sign in there; whether the hub produces a `pairwise-id` for home IdPs that release neither it nor `uid` (frequent outside Spain), or a fallback identifier is needed; the attribute set agreed by the alliance; whether to reuse the existing Aurora service in SIR2 (`es.urv.aurora`), register a dedicated one, or create an Aurora umbrella service for all alliance applications (suggested by RedIRIS); and who registers it in production (URV for the pilot; the operator or the Foundation in scenario 3). |
| 30 | Product name: Open Alliance Course Catalogue (OACC) (confirmed 2026-10-22) | The product is renamed **Open Alliance Course Catalogue (OACC)**, subtitle "the open course catalogue for European University alliances". "Open European Campus Portal" suggested a general campus portal (student services) rather than what the software is: a shared course catalogue for a university alliance. The visible name changes everywhere (README, documentation, `publiccode.yml`, portal and login texts, deployment display names); the **technical identifiers stay**: the `OECP_*` variables, the realm `oecp` (part of the SAML entity ID already sent to the federation), the packages `@oecp/*`, the images `oecp/*`, the error codes `oecp.*` and the OEAPI extension `ext.oecp`. `oecp` is documented as the internal code name. The repository name is the owner's choice (decision pending). Decision 29 is reserved for the federation hub model (SIR2), pending SIR2's answers. |
